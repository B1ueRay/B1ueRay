# Kurazh: план продуктовой аналитики

Внутренний документ команды аналитики. Описывает, что и зачем мы измеряем в Kurazh («Call it or do it.»), как устроен сбор событий, какие воронки, когорты, дашборды и эксперименты нужны, как обращаемся с данными и что поставить в продакшене.

Что уже есть в репозитории:

| Файл | Что это |
| --- | --- |
| `kurazh/analytics.js` | SDK `window.KurazhAnalytics`: журнал событий на устройстве, без сети и сторонних сервисов |
| `kurazh/admin.html` | «Kurazh Insights»: внутренний дашборд по локальному журналу (KPI, воронка, дневная активность, таблица событий, экспорт JSON, демо-данные) |
| `kurazh/docs/analytics-plan.md` | Этот план |

Термины: **Caller** предлагает задание (dare) и подкрепляет его заморозкой (hold) на карте. **Taker** выходит в эфир, задаёт правила (минимальная ставка, минимальный возраст зрителя, категории, типы заданий, бесплатные пропуски) и выполняет или отклоняет задания. Задание засчитано, если ≥60% голосов «да»: заморозки списываются (capture), Taker получает банк минус комиссия платформы 20%. Иначе заморозки снимаются (release). Отказ сверх бесплатных пропусков стоит Taker'у **decline fee**, который уходит вложившимся Caller'ам как **decline bonus**. Отказ «Unsafe» всегда бесплатный. **Courage score** — публичный рейтинг смелости Taker'а.

## 1. North Star и дерево метрик

### 1.1. North Star Metric

**Засчитанные задания в неделю (Weekly Completed Dares, WCD)** — число уникальных заданий, по которым голосование дало ≥60% «да» и заморозки списаны.

Почему эта метрика:

- в одном числе сходятся обе стороны маркетплейса: Caller придумал и оплатил, Taker решился и сделал, зрители проголосовали;
- она напрямую связана с выручкой (комиссия 20% берётся только со списанных заморозок) и с обещанием бренда «Call it or do it»;
- её трудно накрутить без реальной ценности: нужны живой эфир, деньги и голосование.

Сопровождающие (guardrail) метрики, которые не должны ухудшаться при росте WCD:

- доля жалоб на 1000 сессий и доля заблокированных фильтром заданий;
- доля спорных голосований (45–60% «да») и обращений в поддержку по поводу списаний;
- доля «Unsafe»-отказов: рост сигналит, что Caller'ы толкают Taker'ов к опасному;
- чарджбэки и споры по платежам (из данных платёжного провайдера).

### 1.2. Дерево KPI

```
WCD (засчитанные задания / неделя)
├── Предложение (Takers)
│   ├── Активные Takers за неделю (≥1 live_start)
│   │   ├── Новые Takers = регистрации × доля role_select=taker × KYC completion
│   │   ├── Конверсия Caller → Taker (Caller, который впервые вышел в эфир)
│   │   └── Удержание Takers W1 / W4
│   ├── Эфиров на Taker в неделю
│   ├── Средняя длительность эфира (live_end.duration_s)
│   └── Принятые задания на эфир = предложенные × (1 − decline rate − timeout rate)
├── Спрос (Callers)
│   ├── Активные Callers (≥1 stream_view за неделю)
│   ├── Доля Callers, которые вложились (≥1 hold_placed)
│   ├── Заданий, предложенных на эфир (dare_suggest)
│   └── Средняя ставка и число вкладчиков на задание
└── Качество исполнения
    ├── Capture rate = hold_captured / (hold_captured + hold_released)
    ├── Доля голосований с явкой ≥ N голосов
    └── Здоровье Courage score (см. 1.4)

Деньги (производные от WCD)
├── GMV списаний = Σ hold_captured.amount
├── Выручка платформы = 0,2 × GMV списаний
├── Заработок Takers = 0,8 × GMV списаний − decline fee
├── Decline bonuses = Σ decline_bonus.amount
└── Выводы средств = Σ withdrawal_request.amount
```

### 1.3. Конверсия Caller → Taker

Главный рычаг предложения: Taker'ов не хватает всегда, а Caller уже знает продукт.

- **Определение:** доля пользователей, чей первый `role_select` был `caller`, которые в течение 30 дней сделали `role_select {role: taker, first_time: false}` **и** `live_start`.
- **Промежуточные шаги:** открыл экран «Go live» → прошёл KYC → настроил правила → `live_start` → первое засчитанное задание → первый `withdrawal_request`.
- **Срезы:** по числу собственных ставок до перехода (0, 1–3, 4+), по тому, получал ли decline bonus, по категориям эфиров, которые смотрел, по платформе (iOS/Android), по наличию установленного PWA (`standalone`).
- **Цель на запуск:** 5% за 30 дней; ориентир после полугода — 8–10%.

### 1.4. Здоровье Courage score

Courage score публичный, значит это и мотиватор, и мишень для накруток. Отслеживаем:

| Метрика | Норма | Тревожный сигнал |
| --- | --- | --- |
| Распределение по Takers (p10 / p50 / p90) | Широкое, медиана растёт медленно | Сжатие у потолка (инфляция) или у пола (система слишком наказывает) |
| Доля Takers, у которых score вырос за неделю | 40–60% активных | < 25%: правила слишком жёсткие; > 80%: нет различения |
| Корреляция score ↔ удержание Taker W4 | Положительная | Отрицательная: score демотивирует |
| Корреляция score ↔ средняя ставка на эфир | Положительная (Caller'ы доверяют score) | Нулевая: score никто не учитывает |
| Падение score после платного отказа | Умеренное, без оттока | Отток Takers в течение 7 дней после падения > 2× базового |
| Аномалии | Нет | Рост score за счёт кругового голосования одних и тех же аккаунтов, всплески с одного устройства |

Для этого нужно серверное событие `courage_change {delta, reason, band}` (см. 2.3). Считать score на клиенте нельзя: сервер — источник правды.

## 2. Таксономия событий

### 2.1. Общие поля каждого события

Добавляются SDK автоматически, вручную их не передаём.

| Поле | Значение |
| --- | --- |
| `id` | UUID события (дедупликация на сервере) |
| `name` | snake_case, `объект_действие` |
| `props` | Плоский объект: числа, строки до 200 символов, булевы, короткие массивы. Ключи `email`, `name`, `phone` и похожие отбрасываются |
| `ts` | Время на устройстве, мс |
| `session_id` | Новая сессия после 30 минут бездействия |
| `device_id` | Случайный анонимный UUID устройства |
| `user_id` | `s256:` + первые 128 бит SHA-256 от `kurazh:` + id пользователя. Сырой id не хранится. До входа `null` |
| `app_version` | `window.KURAZH_VERSION` или `<meta name="kurazh-version">` |
| `viewport` | `ширинаxвысота` в CSS-пикселях |
| `standalone` | Запущено как установленное PWA |
| `platform` | `ios`, `android`, `macos`, `windows`, `linux`, `other` |
| `consent` | Уровень согласия на момент события: `essential` или `full` |

### 2.2. События

Класс: **E** — операционное, пишется при согласии `essential`; **F** — только при `full`.

| Событие | Когда отправляется | Свойства | Зачем | Класс |
| --- | --- | --- | --- | --- |
| `session_start` | SDK, первое событие после 30 мин бездействия | — | Сессии, частота, удержание | E |
| `app_open` | SDK, раз в сессию: загрузка или возврат в приложение | `referrer` (домен без параметров), `resume` | Вход в воронку, источники трафика | E |
| `page_view` | `KurazhAnalytics.page(name)` при смене экрана | `page` | Навигация, где теряются пользователи | F |
| `client_error` | SDK: необработанная ошибка или rejected promise (до 20 на загрузку) | `kind`, `message` (обрезано, без email и длинных чисел), `source` (имя файла), `line`, `col` | Стабильность релиза | E |
| `perf` | SDK, раз на загрузку страницы | `ttfb`, `fp`, `fcp`, `lcp`, `dom_ready`, `load` (мс) | Скорость на реальных телефонах | E |
| `identify` | После `identify()` при `full` | Трейты без PII (например, `role`) | Склейка устройства и аккаунта | F |

| `login` | Успешный вход с двухэтапной проверкой | `method` | Возвраты, проблемы входа | E |
| `role_select` | Выбор роли на онбординге или смена роли | `role`: `caller` / `taker`, `first_time` | Баланс сторон, конверсия Caller → Taker | F |
| `kyc_start` | Открыт поток проверки личности | — | Воронка KYC | E |
| `kyc_complete` | Провайдер подтвердил личность | — | KYC completion, доступ к деньгам и эфирам | E |
| `stream_view` | Зритель открыл эфир дольше 3 секунд | `stream_id`, `real` (живая камера, а не симуляция) | Спрос, какие эфиры смотрят | F |
| `room_join` | Вход в комнату по ссылке | `real` | Вирусность ссылок на эфир | F |
| `dare_suggest` | Caller отправил задание | `amount`, `type` | Спрос на задания, предпочтения по типам и суммам | F |
| `dare_blocked` | Фильтр безопасности отклонил текст задания | `category` (`dangerous_stunt`, `driving`, `minors`, …) | Безопасность, настройка фильтра | E |
| `dare_decline` | Taker отклонил задание | `reason` (`unsafe`, `not_feeling_it`, `too_hard`, `off_category`, `low_stake`, `already_done`), `fee` (0, если бесплатно) | Decline rate, ценность бесплатных пропусков, Courage score | E |
| `dare_timeout` | Время на принятие или выполнение истекло | — | Потерянные задания, нагрузка на Taker | E |
| `hold_placed` | Провайдер подтвердил заморозку | `amount` | Деньги в работе, средняя ставка | E |
| `hold_captured` | Заморозка списана после зачёта | `amount` | GMV, выручка, North Star | E |
| `hold_released` | Заморозка снята (не засчитано, отказ, таймаут) | `amount` | Capture rate, нагрузка на поддержку | E |
| `decline_bonus` | Caller получил компенсацию за платный отказ | `amount` | Экономика пропусков и сборов | E |
| `vote_cast` | Зритель проголосовал «Does it count?» | `value`: `yes` / `no` | Явка, спорные голосования | F |
| `live_start` | Taker вышел в эфир | `real` | Предложение, активные Takers | E |
| `live_end` | Эфир завершён | `duration_s`, `dares_done`, `earned` | Длительность, продуктивность эфира, заработок | E |
| `withdrawal_request` | Taker запросил вывод | `amount` | Деньги Takers, удержание | E |
| `report_submitted` | Отправлена жалоба | `reason` | Trust & Safety | E |
| `support_open` | Открыт центр поддержки | `topic` | Где пользователи застревают | F |
| `adult_unlock` | Открыт раздел 18+ (после KYC и правил) | — | Комплаенс, доля аудитории 18+ | E |

Правила для инженеров:

- суммы — числа в долларах (`5`, `12.5`), не строки и не центы;
- в `props` нельзя класть свободный текст задания, сообщения чата, ники, email, телефон, номер карты, ID документа;
- `stream_id` — внутренний случайный id, не ник стримера;
- денежные события в продакшене отправляет **сервер** по вебхукам платёжного провайдера. Клиентские события остаются подсказкой для UX-воронок, но не источником учёта.

| Событие | Свойства | Зачем |
| --- | --- | --- |
| `taker_rules_set` | `min_stake`, `min_viewer_age`, `categories_n`, `types_n`, `free_passes` | Как правила Taker'а влияют на спрос; основа экспериментов с пропусками |

## 3. Воронки и когорты

### 3.1. Воронки

1. **Основная активация** (в `admin.html`, по уникальным устройствам):
   `app_open → signup_complete → role_select → kyc_complete → hold_placed → hold_captured`.
2. **Регистрация по методу:** `signup_start → signup_complete` отдельно для Google и email. Ожидаем, что Google конвертирует на 15–25 п. п. лучше. Если разрыв больше, проверяем email-код и SMS.
3. **Деньги Caller'а:** `stream_view → dare_suggest → hold_placed → (dare_accept) → vote_cast → hold_captured`. Отдельно считаем утечки: `dare_blocked`, `dare_decline`, `dare_timeout`, `hold_released`.
4. **Путь Taker'а:** `role_select(taker) → kyc_start → kyc_complete → (taker_rules_set) → live_start → первое hold_captured → withdrawal_request`.
5. **Жизненный цикл задания** (по `dare_id`, когда он появится в событиях): предложено → принято / отклонено (по причине, платно или бесплатно) / таймаут → выполнено → голосование → списано или снято.

Окна конверсии: 1 сессия для регистрации, 7 дней для KYC и первой ставки, 30 дней для Caller → Taker.

### 3.2. Когорты

| Когорта | Ключ | Что смотрим |
| --- | --- | --- |
| Недельная по первому `app_open` | неделя установки | Удержание D1, D7, D30 (любое событие), доля дошедших до `hold_placed` |
| По методу регистрации | `signup_complete.method` | Удержание, KYC completion, средняя ставка |
| По первой роли | первый `role_select.role` | Удержание, конверсия Caller → Taker, денежная ценность |
| Денежная | неделя первого `hold_placed` | Накопленный GMV на пользователя через 4 и 12 недель, повторные ставки |
| Takers | неделя первого `live_start` | Эфиров в неделю, заработок, отток после платного отказа или падения Courage score |
| Платформа | `platform`, `standalone` | Влияние установки PWA на удержание (гипотеза: +30–50% D7) |

## 5. A/B-тесты

Общие правила:

- **Единица рандомизации** зависит от стороны: для настроек Taker'а — Taker (все его эфиры в одной группе), для интерфейса Caller'а — пользователь. Для эффектов, которые перетекают между сторонами (пропуски и сборы меняют поведение обеих), — рандомизация по Taker'ам плюс контроль доли Caller'ов, которые видят оба варианта.
- **Размер выборки** (ориентир): для бинарной метрики с базой 34% и минимальным эффектом +3 п. п. при α = 0,05 и мощности 80% нужно около 3 900 единиц на группу. На раннем этапе тестируем только крупные эффекты (≥ 5 п. п.) или используем CUPED.
- Минимальная длительность 2 полные недели (недельная сезонность эфиров). Не подглядываем: решение по заранее заданному сроку или по последовательному тесту.
- Каждый тест имеет guardrails из 1.1.

| # | Тест | Варианты | Гипотеза | Основная метрика | Guardrails |
| --- | --- | --- | --- | --- | --- |
| 1 | **Пресеты ставок по умолчанию** | A: $5 / $10 / $20 (контроль); B: $10 / $20 / $50; C: $3 / $5 / $10 | Высокие якоря поднимают среднюю ставку без потери доли вложившихся; низкие увеличивают долю первых ставок | GMV списаний на активного Caller'а | Доля Callers с ≥1 `hold_placed`, отказы банков, жалобы на списания |
| 2 | **Бесплатные пропуски** | 1 / 3 / 5 за эфир (сейчас 2) | Больше пропусков → Takers чаще выходят в эфир и дольше остаются, но decline rate растёт | Эфиров на Taker в неделю, удержание Taker W4 | WCD на эфир, decline rate, доля Callers, получивших отказ дважды подряд |
| 3 | **Размер decline fee** | 10% / 20% / 30% от банка задания | Выше сбор → меньше платных отказов, но больше «Unsafe»-отказов и оттока Takers | Decline rate (платные), WCD | Доля «Unsafe»-отказов (подмена причины), отток Takers 7 дней, decline bonus на Caller'а |
| 4 | **Подача порога голосования** | A: «60% Yes to count»; B: живой индикатор «нужно ещё N голосов»; C: формулировка от лица Taker'а: «Help them get it counted» | Ясная прогресс-подача повышает явку и уменьшает спорные результаты | Явка в голосовании (`vote_cast` на зрителя эфира) | Доля спорных голосований 45–60%, обращения в поддержку «несправедливо не засчитали» |

Дополнительные идеи после первых тестов: показ Courage score на карточке задания, напоминание о decline bonus в уведомлении, подсказка «Go live yourself» после третьей ставки (рычаг Caller → Taker).

## 6. Управление данными

### 6.1. Согласие

- **`essential`** (по умолчанию): только операционные события (класс E в 2.2): сессии, ошибки, производительность, аккаунт, деньги, безопасность, комплаенс. Нужны для работы сервиса и учёта, основание — исполнение договора и законный интерес.
- **`full`**: плюс поведенческие события (класс F): просмотры, навигация, голоса, выбор роли. Только по явному согласию в баннере или в Settings → Privacy.
- `navigator.doNotTrack = 1` или Global Privacy Control принудительно оставляют `essential`, даже если пользователь выбрал `full`.
- Понижение до `essential` сразу удаляет с устройства уже собранные поведенческие события.
- Выбор согласия меняется в любой момент и не влияет на доступ к функциям.

### 6.2. Хранение

| Где | Что | Срок |
| --- | --- | --- |
| Устройство (`kurazh.analytics.v1`) | Сырые события | До 5000 событий (FIFO) и не старше 90 дней |
| Сервер, сырые события | Все события с псевдонимным `user_id` | 13 месяцев, затем удаление |
| Сервер, `client_error` и `perf` | Технические данные | 30 дней сырых, дальше агрегаты |
| Сервер, агрегаты | Дневные метрики без `user_id` и `device_id` | Бессрочно |
| Деньги и KYC | Не в аналитике: у платёжного и KYC-провайдеров и в бэкенде | По финансовому и AML-законодательству (обычно 5+ лет) |

### 6.3. Персональные данные

- В событиях никогда нет email, имени, телефона, адреса, даты рождения, данных карты, документа, селфи, текста заданий и чата. SDK отбрасывает такие ключи и маскирует email и длинные числа в строках.
- `user_id` — хеш с солью. Это **псевдонимизация, а не анонимизация**: по GDPR такие данные остаются персональными. На сервере хеш пересчитывается через HMAC-SHA-256 с секретной солью из хранилища секретов, клиентский хеш используется только для склейки.
- Удаление аккаунта: по `user_id` удаляем сырые события на сервере в течение 30 дней, агрегаты не трогаем.
- Доступ к сырым данным — роль «аналитик» по SSO с журналом доступа. Выгрузки только агрегатами. `admin.html` не публикуется в продакшене или закрывается авторизацией.
- Раздел 18+: в аналитику пишется только факт `adult_unlock` и категория эфира `18+`, без содержимого эфиров.
- Ведём реестр обработки (RoPA) и DPIA для Trust & Safety и раздела 18+; с каждым подрядчиком — DPA, хранение в ЕС для пользователей из ЕС.

## 7. Стек для продакшена

### 7.1. Архитектура

```
PWA (analytics.js)  ──batch POST /e (sendBeacon, при согласии)──►  Edge-эндпоинт сбора
Бэкенд (деньги, голосование, Courage score) ──server events──►      │  валидация схемы, HMAC user_id,
Вебхуки платёжного и KYC-провайдеров ─────────────────────────►     │  отбрасывание IP, гео до страны
                                                                    ▼
                                                     Очередь (Kafka / Redpanda / SQS)
                                                                    ▼
                                         ClickHouse (или BigQuery) — сырые события
                                                                    ▼
                                         dbt: модели сессий, воронок, когорт, денег
                                                                    ▼
                         BI (Metabase / Superset)  ·  эксперименты (GrowthBook)  ·  алерты (Grafana)
```

SDK меняется минимально: к текущему журналу добавляется отправка пачками раз в 10–30 секунд и при `pagehide` через `navigator.sendBeacon`, с повтором при ошибке сети. Локальный журнал остаётся для офлайна.

### 7.2. Варианты и ориентировочная стоимость

Цены ориентировочные (уровень конца 2026 года, без НДС). Перед закупкой проверить на сайте поставщика.

| Компонент | Рекомендация | Альтернатива | Стоимость при ~1 млн событий/мес | При ~50 млн событий/мес |
| --- | --- | --- | --- | --- |
| Эндпоинт сбора | Cloudflare Workers | Небольшой сервис на Go в том же облаке | $0–5 | $20–60 |
| Очередь | Не нужна на старте (пишем прямо в ClickHouse пачками) | Redpanda / AWS SQS | $0 | $50–200 |
| Хранилище | ClickHouse self-hosted (Hetzner, ЕС) | ClickHouse Cloud, BigQuery | $40–80 (1 сервер) | $150–600 |
| Трансформации | dbt Core | dbt Cloud | $0 | $0–100 |
| BI | Metabase OSS | Superset, Metabase Cloud ($100+) | $0 (на том же сервере) | $0–100 |
| Эксперименты и флаги | GrowthBook self-hosted | PostHog Feature Flags | $0 | $0–200 |
| Ошибки фронтенда | GlitchTip self-hosted (совместим с Sentry SDK) | Sentry Team (~$26+) | $0–26 | $26–100 |
| **Итого** | | | **≈ $50–120 / мес** | **≈ $300–1 300 / мес** |

Готовая альтернатива «всё в одном»: **PostHog Cloud EU** (продуктовая аналитика, воронки, когорты, флаги, A/B). Первые ~1 млн событий в месяц бесплатно, дальше порядка $0,00005 за событие с понижением на объёме: ~$0 на старте и ~$1 500–2 500 в месяц на 50 млн событий. Быстрее запуститься, но дороже на объёме и данные у подрядчика. Self-hosted PostHog возможен, но требует отдельной инфраструктуры.

**Рекомендация.** До 5–10 млн событий в месяц: PostHog Cloud EU с отключённым автосбором, записью сессий и IP. Отправляем туда только события из этой таксономии через наш эндпоинт, который убирает лишнее. После 10 млн событий или при росте требований комплаенса раздела 18+: переход на ClickHouse + dbt + Metabase + GrowthBook в собственном облаке ЕС. Таксономия и SDK при этом не меняются.

### 7.3. Порядок внедрения

1. Подключить `analytics.js` в `index.html` и расставить вызовы из 2.2 (инженерия). Баннер согласия и переключатель в Settings → Privacy.
2. Серверные денежные события по вебхукам провайдера, сверка с журналом провайдера раз в сутки.
3. Эндпоинт сбора, хранилище, первые дашборды: Executive weekly и Trust & Safety.
4. События из 2.3 и `dare_id` во всех событиях задания.
5. GrowthBook и первые два эксперимента: пресеты ставок и бесплатные пропуски.
